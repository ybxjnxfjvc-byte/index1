# Карта практических доказательств Product × Security

Эта страница отвечает на вопрос работодателя: **«какими файлами подтверждается практическая часть?»**

| Навык | Что сделано в кейсе | Проверяемый артефакт |
|---|---|---|
| Постановка задачи | Зафиксированы пользователь, сценарий, границы и критерии готовности | `docs/brief.md` |
| Пользовательский маршрут | Описан flow и ошибочные ветки | `docs/user-flow.md` |
| Доступность | Чек-лист клавиатуры, focus, заголовков и reduced motion | `docs/a11y-check.md` |
| Модель данных | Поля результата классифицированы по цели и чувствительности | `docs/data-model.md` |
| API/JSON | Описаны разрешённые поля, статусы 400/401/413/500 и примеры | `docs/api-contract.md`, `examples/api/*` |
| Недоверенный ввод | Имя и подразделение рассматриваются как недоверенные строки; в публичном UI выводятся через `textContent` | `docs/input-validation.md`, браузерный тест |
| SQL | Локальная запись результата выполнена только параметризованными запросами | `lab/sqlite_store.py`, Python-тест |
| Авторизация | Учебный локальный API требует bearer-токен из переменной окружения | `lab/mock_api.py`, `.env.example` |
| Секреты | Реальные секреты запрещены; `.env` исключён из Git | `.gitignore`, `.env.example`, `scripts/security_check.py` |
| Модель угроз | Активы, роли, границы доверия, минимум пять рисков и локальные проверки | `docs/threat-model.md` |
| Логи | Журнал не содержит пароль, токен, e-mail, телефон или полный свободный ввод | `docs/logging-policy.md` |
| Ошибки | Клиенту возвращается минимальная ошибка без stack trace | `docs/error-policy.md`, `lab/mock_api.py` |
| Локальная диагностика | Описаны порт, процесс, health-check и остановка сервиса | `docs/local-ops.md` |
| Ручное QA | 12 тест-кейсов, включая негативные и security-сценарии | `tests/manual-checklist.md` |
| Автотесты | API/SQL + браузерный smoke/security тест | `tests/python/*`, `tests/playwright/*` |
| CI | При push/PR запускается статический security-check и Python-тесты | `.github/workflows/security-check.yml` |
| Предпубликационный аудит | Проверка архивов, секретов, персональных данных и лишних файлов | `docs/prepublish-check.md` |
| Ретроспектива | Зафиксировано, что доказано, а что кейс не доказывает | `docs/retrospective.md` |

## Что этот кейс доказывает

1. Умение видеть поверхность атаки даже у небольшого статического продукта.
2. Умение отделять пользовательский ввод от доверенных констант интерфейса.
3. Умение проектировать минимальный серверный контур с валидацией, аутентификацией, ограничением размера запроса и безопасными логами.
4. Умение работать с SQLite через placeholders, а не конкатенацию SQL.
5. Умение сделать проверку воспроизводимой: документация → тест → CI → отчёт.

## Что этот кейс НЕ доказывает

- аудит или тестирование внутренних систем Сбербанка;
- доступ к продуктивной инфраструктуре, SOC, SIEM, банковским данным или закрытым API;
- проведение внешнего pentest реального банка;
- промышленную эксплуатацию учебного локального API.

Это намеренное ограничение: сильное утверждение в портфолио должно быть связано только с доступным артефактом.
